## Usage

```bash
ocx opencode [options] [args...]
ocx oc [options] [args...]  # alias
```

## Description

Launch OpenCode with resolved configuration and profile support. OCX merges profile settings, discovers instruction files, applies pattern filtering, and spawns OpenCode with the final configuration.

## Flags

| Flag | Shorthand | Default | Description |
|------|-----------|---------|-------------|
| `--profile <name>` | `-p` | | Use specific global profile |
| `--no-rename` | | `false` | Skip automatic window/terminal renaming |

<Note>
Only `-p`/`--profile` and `--no-rename` are OCX flags. All other arguments and flags pass through to OpenCode. Use `--` to pass flags that conflict with OCX (e.g., `ocx oc -- --help` forwards help to OpenCode).
</Note>

## Examples

### Launch with Default Profile

```bash
ocx opencode
```

### Launch with Specific Profile

```bash
ocx opencode -p work
```

### Skip Window Renaming

```bash
ocx opencode --no-rename
```

### Use Environment Variable

```bash
OCX_PROFILE=work ocx opencode
```

### Use the Short Alias

```bash
ocx oc -p personal
```

### Pass Flags to OpenCode

```bash
# Get help from OpenCode itself
ocx oc -- --help
```

## Profile Resolution Priority

Profiles are resolved in this order (first match wins):

1. **`--profile` / `-p` flag** — Explicit CLI specification
2. **`profile` field in `.opencode/ocx.jsonc`** — Project-specific profile
3. **`OCX_PROFILE` environment variable** — Session-level profile
4. **`default` profile** — If it exists
5. **No profile** — Base configurations only

## How It Works

1. **Profile Resolution**: Resolves profile using the priority order above.
2. **Instruction Discovery**: Discovers instruction files in priority order.
3. **Pattern Filtering**: Applies exclude/include patterns from profile.
4. **Launch OpenCode**: Spawns with profile configuration and discovered instructions.

**Registry Isolation:**

Global base config registries (`~/.config/opencode/ocx.jsonc`) are **only** used for downloading profiles, never for components. When using a profile, registries come from the profile config. This isolation prevents global registries from injecting components into all projects.

## Custom OpenCode Binary

To use a custom OpenCode binary, set the `bin` option in your profile's `ocx.jsonc`:

```jsonc
{
  "bin": "/path/to/custom/opencode"
}
```

**Resolution order:**

1. `bin` in profile's `ocx.jsonc`
2. `OPENCODE_BIN` environment variable
3. `opencode` (system PATH)

## Background Server Fallback (OpenCode v2)

OpenCode v2 clients normally connect to a shared background server. When that
server is not running, a plain launch can hang or fail in some environments.
Before spawning, `ocx oc` probes `opencode service status` and applies the
`serverFallback` mode from your profile's `ocx.jsonc`:

| Mode | Behavior when the background server is stopped |
|------|-----------------------------------------------|
| `standalone` (default) | Launch with `--standalone` (private server) and print a warning to stderr |
| `start` | Run `opencode service start` first; if it fails or times out, fall back to `--standalone` |
| `none` | Never intervene — launch passes through to OpenCode unchanged |

```jsonc
{
  "serverFallback": "start"
}
```

**Environment override:** set `OCX_SERVER_FALLBACK` to `standalone`, `start`, or
`none` (also accepts `0`/`false`/`off` to disable, or `1`/`true` to use the
profile config). Invalid values fail fast.

<Note>
The probe is fail-open: if `opencode service status` errors, times out (~3s),
or is unavailable (OpenCode v1), OCX launches unchanged — the fallback never
blocks a launch. Explicit `--standalone` or `--server` arguments always win and
disable the probe entirely. The fallback only applies to TUI-style launches;
subcommands like `ocx oc serve` or `ocx oc run` are passed through untouched.
</Note>
